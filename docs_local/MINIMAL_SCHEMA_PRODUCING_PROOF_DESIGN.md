# Minimal Schema Producing Proof Design

## 1. Purpose

This document designs the first proof that current Agent/tool outputs can be
converted into the MVP Research Workspace Report Schema.

The goal is to validate the conversion path:

```text
Tool Result
    -> Validated Data
    -> Structured Research Report Schema
    -> AI Interpretation
```

This is design only. It does not implement a schema builder, modify AgentLoop,
change providers, run Web UI, or call live data.

## 2. What the Proof Should Prove

The proof should answer one product question:

```text
Can one explicit stock research request produce a complete structured report
object instead of only free-form Markdown?
```

Target symbol:

```text
600519.SH
```

Minimum required sections:

* `symbol`
* `market_snapshot`
* `financial_health`
* `investment_memo`
* `data_confidence`

Optional later sections:

* `valuation`
* `risks`
* `limitations`

## 3. Schema Producer Responsibilities

The Schema Producer is the layer that turns validated tool results into a
structured research report object.

It should not be a pure LLM free-form generator.

Recommended responsibility split:

```text
Tool-derived facts      -> program fills schema fields
Data quality metadata   -> program fills confidence fields
AI interpretation       -> Agent/LLM fills memo fields
Unsupported capability  -> program or policy fills limitations
```

### Fields Filled by Tool Data

These fields must come from tool output or validated metadata:

* `symbol.normalized_symbol`
* `symbol.market`
* `symbol.asset_type`
* `market_snapshot.price`
* `market_snapshot.change`
* `market_snapshot.change_pct`
* `market_snapshot.volume`
* `market_snapshot.turnover`
* `financial_health.statements[].provider`
* `financial_health.statements[].source`
* `financial_health.statements[].upstream`
* `financial_health.statements[].period`
* `financial_health.statements[].latest_data_date`
* `financial_health.statements[].metrics`
* `data_confidence.market_data`
* `data_confidence.financial_data`
* `data_confidence.warnings`

### Fields Filled by Agent / LLM

These fields may be generated by the Agent after validated data exists:

* `market_snapshot.trend.summary`
* `financial_health.summary.revenue_trend`
* `financial_health.summary.profit_trend`
* `financial_health.summary.balance_sheet_view`
* `financial_health.summary.cashflow_view`
* `investment_memo.thesis`
* `investment_memo.bull_case`
* `investment_memo.bear_case`
* `investment_memo.key_risks`
* `investment_memo.monitor_items`

### Fields Forbidden for LLM Inference

The LLM must not invent or infer these fields without tool data:

* price
* change / change percent
* volume
* turnover
* revenue
* net profit
* assets
* liabilities
* operating cash flow
* provider
* source
* upstream
* report date / period
* data quality status
* fallback status
* PE / PB / target price
* analyst forecast
* shares outstanding / market cap unless retrieved

If these values are missing, the schema should carry `missing`, `partial`, or a
warning. The Agent should not fill the gap with prose.

## 4. Minimal Proof Scope

The first proof is intentionally narrow.

Input:

```text
请分析 600519.SH 的市场表现、财务健康和主要风险。只使用实际获取到的数据，不要估算。
```

Target symbol:

```text
600519.SH
```

Required tools:

* Market data tool for `market_snapshot`.
* Financial statements tool for `financial_health`.

Required financial statements:

* `income`
* `balance`
* `cashflow`

Required output sections:

```json
{
  "symbol": {},
  "market_snapshot": {},
  "financial_health": {},
  "investment_memo": {},
  "data_confidence": {}
}
```

Out of scope:

* Web UI.
* Markdown report rendering.
* Portfolio context.
* Peer comparison.
* Valuation engine.
* Forecasting.
* Full market overview.

## 5. Data Flow

Recommended proof flow:

```text
User Query
    -> Agent Plan
    -> Tool Calls
    -> Validated Data
    -> Schema Builder
    -> AI Interpretation
    -> Research Report
```

### Step 1: User Query

Input should be explicit for the proof:

```text
600519.SH
```

Reason:

This proof is about schema production, not symbol normalization.

### Step 2: Agent Plan

Agent decides it needs:

```json
{
  "need_market_snapshot": true,
  "need_financial_health": true,
  "need_investment_memo": true,
  "need_data_confidence": true
}
```

Policy:

The plan should not include unsupported valuation, target price, or forecast
unless requested and explicitly marked unavailable.

### Step 3: Tool Calls

Expected minimum calls:

```text
get_market_data(600519.SH)
get_financial_statements(600519.SH, income)
get_financial_statements(600519.SH, balance)
get_financial_statements(600519.SH, cashflow)
```

All calls must pass existing guards:

* Symbol Intent Guard.
* Asset-type Routing Guard.
* Benchmark Policy where relevant.

### Step 4: Validated Data

Each tool result must be inspected for:

* provider
* source
* date or reporting period
* status
* warnings
* `_data_quality`

If this metadata is missing, the Schema Producer must mark the section as
`partial` or `unknown`.

### Step 5: Schema Builder

Programmatic assembly should fill the stable data fields:

```text
validated market data      -> market_snapshot
validated financial data   -> financial_health.statements
data quality metadata      -> data_confidence
unsupported items          -> limitations
```

The Schema Builder should produce a partial schema even if some sections fail.

### Step 6: AI Interpretation

Only after raw data is assembled should the Agent/LLM generate:

* trend summary
* financial interpretation
* thesis
* bull case
* bear case
* risks
* monitor items

The prompt to the LLM should include:

* the partial schema
* data confidence metadata
* unsupported capability list
* instruction not to fill missing numeric fields

### Step 7: Research Report

Final output should include:

* structured JSON-like report object
* optional human-readable markdown view

The JSON-like object is the source of truth. Markdown is only presentation.

## 6. Field Source Map

| Schema section | Field examples | Source |
| --- | --- | --- |
| `symbol` | input, normalized_symbol, market, asset_type | Symbol resolution / guards |
| `market_snapshot` | price, change_pct, volume, turnover | market data tool |
| `market_snapshot.trend.summary` | plain-language trend interpretation | AI interpretation from market data |
| `financial_health.statements` | provider, source, period, metrics | financial statements tool |
| `financial_health.summary` | revenue/profit/cash-flow interpretation | AI interpretation from statements |
| `investment_memo` | thesis, bull_case, bear_case, monitor_items | AI interpretation |
| `data_confidence.market_data` | provider, date, status, warnings | market data `_data_quality` |
| `data_confidence.financial_data` | provider, source, period, status, warnings | financial `_data_quality` |
| `limitations` | unsupported capabilities | capability contract / policy |

## 7. Failure Behavior

### Market Data Missing

If market data is missing:

* `market_snapshot.status = "missing"`
* price fields remain `null`
* `data_confidence.market_data.status = "missing"`
* Agent must not write price-related conclusions.

Allowed interpretation:

```text
未能取得可用行情数据，因此不分析价格、涨跌幅或成交情况。
```

### Market Data Stale / Unknown

If market data is stale or timestamp unknown:

* `market_snapshot.status = "partial"` or `unknown`
* time-sensitive claims should be blocked or downgraded
* warnings must be visible in `data_confidence`

### Financial Data Missing

If financial statements are missing:

* `financial_health.status = "missing"`
* `financial_health.statements = []`
* Agent must not write revenue/profit/cash-flow conclusions.

Allowed interpretation:

```text
未能取得可用财务报表，因此不生成财务趋势结论。
```

### Partial Financial Data

If only some statements are available:

* `financial_health.status = "partial"`
* available statements are included
* missing statements are listed in warnings
* Agent can discuss available statements only

### Provider Failure

If a provider fails:

* failure must enter `data_confidence.warnings`
* fallback use must enter `data_confidence.warnings`
* primary and fallback sources must not be confused

Example warnings:

```text
primary_financials_unavailable
a_stock_data_fallback_used
a_stock_data_fallback_failed
```

### Unsupported Capability

If the user asks for unsupported outputs:

* unsupported item goes to `limitations.unsupported`
* report should explain what can be provided instead

Examples:

* target price
* analyst forecast
* peer comparison
* real-time financial change

## 8. Recommended Proof Architecture

Recommended option:

```text
Hybrid Schema Producer
```

Program fills:

* identifiers
* numeric fields
* provider/source
* dates/periods
* quality metadata
* missing/partial states

LLM fills:

* thesis
* bull case
* bear case
* risks
* monitor items
* interpretation summaries

Reason:

This avoids the two main failure modes:

* LLM-only JSON can omit or hallucinate fields.
* Program-only schema cannot produce useful investment interpretation.

## 9. Proof Acceptance Criteria

For `600519.SH`, success means a complete schema object includes:

```json
{
  "symbol": {
    "normalized_symbol": "600519.SH"
  },
  "market_snapshot": {
    "status": "available"
  },
  "financial_health": {
    "statements": []
  },
  "investment_memo": {
    "bull_case": []
  },
  "data_confidence": {
    "warnings": []
  }
}
```

More detailed acceptance:

* `symbol.normalized_symbol` exists.
* `market_snapshot` exists even if market data is partial/missing.
* `financial_health.statements` contains income, balance, and cashflow when
  available.
* `investment_memo` exists and follows the fixed structure.
* `data_confidence` includes provider/source/status/warnings.
* Provider failure and fallback usage are visible.
* Missing fields are represented as `null`, `missing`, `partial`, or warnings.
* No unsupported numeric values are invented by the LLM.

Failure means:

* price or financial numbers are filled without tool evidence
* provider/source disappears
* quality metadata disappears
* Markdown becomes the only output
* unsupported valuation or forecast appears as fact

## 10. What This Proof Does Not Do

Do not do in this phase:

* Modify AgentLoop.
* Modify Web UI.
* Modify provider chain.
* Connect a real schema builder.
* Add new live data calls.
* Add new data sources.
* Build React components.
* Build charts.
* Implement Metrics Engine.
* Implement valuation.

Recommended next task:


The first implementation, if approved later, should be a CLI/local script, not
Web UI. It should prove that validated tool results can produce the schema
before the UI consumes it.

```text

2. CLI schema proof with controlled live/direct tool outputs

```
